# Pre-registration: confirmatory re-run, 2026-10-18

Committed before the sweep. Anything run after it is exploratory and is
labelled so.

## Server under test

`plant-genomics-mcp==1.29.2` from PyPI, the version the 2026-10-16 sweep ran,
launched by `uvx --exclude-newer 2026-10-17T00:00:00Z`. No server code
changed, so there is no `--server-spec`: 1.29.3, the current release, differs
from 1.29.2 only in its version string (`git diff v1.29.2 v1.29.3 -- src`).
Every mcp row records the pin, and `versions.json` records it with the Claude
Code version and the key's sha256.

## Why no server change

`diagnose.py` on the 468 transcripts of 2026-10-16 (prices fitted to each
model's `costUSD`, worst residual $8e-16):

| | first-call context | API calls / run | tool input chars (median) | tool output chars (median, mean) | cost split |
|---|---|---|---|---|---|
| mcp | 28,015 tokens, 56 tools | 2.24 | 54 | 385, 695 | cache reads 48%, cache writes 32%, output 20% |
| web | 2,069 tokens, 2 tools | 4.74 | 194 | 348, 2,874 | cache writes 37%, output 35%, cache reads 12%, searches 11%, page reader 5% |

The three surface faults found in the other servers are absent here. No call
was refused for a bare tool name (0 permission denials; the server sends no
instructions, and its descriptions name other tools only as advice). No
payload was pasted into a call (median input 54 characters). Outputs are
short (median 385 characters). What the server costs is its 56 tool
definitions, about 27,300 tokens sent with every API call and read from cache:
about 47% of its spend. Shortening them is a change to the public surface
whose effect on accuracy, this sweep's endpoint, is unknown, so it is left for
a separate experiment and not mixed into this one.

The 10-16 questions put web search at 151 of 156 and the server at 156 of
156, so they cannot show a difference. This sweep uses a new, harder set.

## Questions

`build_hard.py` (seed 20261018) reads Ensembl REST, UniProt REST and NCBI
E-utilities over httpx without importing `plant_genomics_mcp`. It froze
36 questions at 2026-10-18T19:25:38Z to
`~/plant-genomics-mcp-artifacts/agent_qa/rerun-2026-10-18/questions.json`
(sha256 `f8a5e2b6b7b7782c2f46fc9bc3e40a6e7ff6fe0f83e00b930335d7c1437ea957`, outside the repo), on Ensembl 116 / Ensembl Genomes
63 and UniProt 2026_03 (02 September 2026). Kinds, from the README's tool matrix (homology,
cross-references, region query, UniProt resolution), six each:

| Kind | Question |
|---|---|
| ortholog_location | an Arabidopsis gene's one-to-one Ensembl Compara ortholog in rice, maize, sorghum, tomato, soybean or grapevine: its chromosome and start |
| ortholog_protein_length | the same, then the canonical protein length of the ortholog (barley, Brachypodium, poplar, Medicago, rice, maize) |
| symbol_ortholog | an Arabidopsis UniProt gene name, to its locus, to its one-to-one ortholog |
| id_mapping | 3 rice RAP-DB → MSU loci (UniProt); 3 Arabidopsis AGI → NCBI Gene IDs (Ensembl xrefs, confirmed at NCBI) |
| position_to_gene | the only gene at a position of an assembly (maize, wheat, soybean, sorghum, Medicago, barley) |
| interval_count | protein-coding genes overlapping a 150–400 kb interval (8–45 genes) |

Every question names the database the key holds (Ensembl Plants, Ensembl
Compara, UniProt or NCBI Gene) and, for coordinates, the assembly. Oracle on
this key: 36 of 36 key answers score right, and 0 of 36 answers moved
to the next question of the same kind do. `run.py` checks this before the
sweep, and stops if Ensembl or UniProt serve another release than the key's.

## Arms, reps, order

- `web`: WebSearch and WebFetch only, as on 10-16.
- `mcp`: plant-genomics-mcp 1.29.2 only, as on 10-16.
- Same model (`claude-opus-5-5`), system prompt, answer format, isolation
  and validity rule as on 10-16. Each run gets its own `TMPDIR`.
- `bare` is not re-run, and no 10-16 row is used.
- 3 reps, in rep, then question, then arm order (bare skipped; web, then
  mcp), so the arms are interleaved by question. One worker, under
  `flock … env HEAVY_RUN_MEM=6G heavy-run`.
- Output: `~/plant-genomics-mcp-artifacts/agent_qa/rerun-2026-10-18/`
  (`results.jsonl`, `versions.json`, `pauses.jsonl`, transcripts in `runs/`).

## Primary endpoint and win rule

Primary endpoint: questions right in all 3 runs, mcp against web, out of
36. An invalid run (the 10-16 validity rule: exit, tools, server
connected, no tool call, leak scan) does not count as right.

- **Non-inferior:** mcp ≥ web − 2.
- **Better:** an exact two-sided McNemar test on the discordant questions
  gives p < 0.05 with more questions that only mcp got right, and the
  bootstrap 95% CI (10,000 resamples of questions, seed 20261018) of
  (mcp − web) / 36 lies wholly above 0.
- **WIN** = non-inferior and better. **LOSS** = not non-inferior, or web
  significantly better (p < 0.05, CI wholly below 0). Anything else is a
  **TIE**. Implemented as `analyze_rerun.win_rule` and tested in
  `tests/test_agent_qa_rerun.py`.

Secondary (reported, not deciding): right per run; cost, seconds and tool
calls per answer (bootstrap ratios, sign tests); the no-model baselines;
accuracy by kind; the mechanism readout (how many mcp runs called each tool,
error results, calls refused by the client); `diagnose.py` on the new
transcripts.

Expectation, written down so it can be wrong: the server should lead on
interval counts and on position-to-gene, where web search must read a long
JSON list through WebFetch's summarizer, and on the two-step ortholog kinds.
The server's ortholog tool reads Gramene (an older Compara build) while the
key holds Ensembl Compara, so where the two disagree the server can be wrong;
that is a property of the server and stays in. NCBI Gene IDs and MSU loci
are one page each for web search and should be even.

## Usage limits and harness failures

Start only if the newest transcript's five-hour utilization is below 0.50 and
seven-day below 0.80. `run.py` pauses until `resetsAt` whenever a transcript
shows five-hour utilization ≥ 0.85 or a `rejected` status, records each pause
in `pauses.jsonl`, and stops if seven-day utilization is ≥ 0.80. A row the
API ended before the model answered (`run.api_failure`: a rate-limit
rejection with no successful result, or terminal reason `api_error`, decided
from the transcript alone) is a harness failure. After the sweep,
`run.py --drop-api-failures` sets these aside and the sweep is resumed to
re-run each once; a row the API ends again stays in and counts as invalid.
Timeouts are not re-run. An interrupted sweep is resumed, never restarted,
and never stopped early on interim results.
